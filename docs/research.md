# 调研、实测与设计依据

本文只记录可公开复用的架构依据、通用工程经验和公开来源。任何部署产生的医院名称、供应商、产品版本、内部地址、账号角色、页面截图、UI 路径及资格证据均属于私有 site profile，不进入本文或 Git 历史。部署档案边界见[部署档案配置](site-integration.md)。

## 已确认的产品决策

- 产品名称为 Med Auto Practice（MAP），定位为可供宿主和其他 Agent 调用的临床工作 Agent，不默认建设独立 UI。
- 一期包含既往和当下临床工作；专病队列与动态随访后置。实施顺序按共同依赖组织，不以单个演示任务替代一期范围。
- 医学提案、业务工作流和医院系统适配分别维护。医学实现不持有系统写入权限；工作流负责任务步骤、规则和复核；适配器负责可见系统操作及回读。
- 医院系统保有正式病历与医嘱状态；医生负责临床决定和签署。MAP 记录任务状态、证据引用、草稿、审批和回读。
- 同一工作流可组合原生 API、院内中间件、宿主 Computer Use 和 IP KVM。患者绑定、来源、审批与目标对象回读随任务贯通。

## 通用工程依据

- KVM 画面没有通用 Windows 控件树。适配器应实现语义操作，并将页面识别、字段锚点、前后状态、等待和恢复规则封装在部署 profile 中；不可复用历史坐标作为稳定接口。
- 每次操作都需绑定患者、就诊、来源范围与当前资源版本或界面观察。跨系统切换后重新核对唯一标识；姓名或床号不足以消歧。
- 观察和写入是不同资格。写入后需从目标系统重新打开对象核验内容、状态和对象身份；响应不确定时只回查，不自动重放。
- 中文长文的输入与逐段回读需单独取得资格。未合格时提供可审阅草稿，不推断保存成功。
- 检验、护理、影像、输血等事实必须保留来源、发生时间、记录时间、单位、状态、查询范围和覆盖完整性；缺失与阴性结果不得混同。
- 记录厂商、版本和规则来源时以部署方现场证据为准。公开标准可用于通用数据模型参考，不能替代院内字典、模板、权限与时限。

## 当前公开仓库状态

公开仓库提供医学提案路由、一期工作流合同、合成数据任务内核、通用站点依赖模板和本地只读计划工具。所有临床能力仍由 `contracts/capabilities.json` 标记为未开放。具体部署状态由 `MAP_SITE_PROFILE` 指定的仓库外 JSON 文件提供，不随源码发布。

验证仓库：

```sh
python3 scripts/project_status.py --json
python3 scripts/site_plan.py revise_orders
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

所有自动化测试使用合成数据，不连接医院或患者系统。状态检查、依赖计划和测试通过都不代表临床资格。
