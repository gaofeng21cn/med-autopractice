# 病历收集与结构化

本页是「收集 → 清洗 → 结构化病历」这条链路的 SSOT。它定义产物、清洗规则和
不可逾越的边界；具体页面操作属于部署档案，见
[院内系统调研与操作档案](site-survey.md)。机器可读合同见
[structured-clinical-record.schema.json](../contracts/structured-clinical-record.schema.json)。
下一层（固定列、归一化编码、可跨病例合并的研究长表）见
[研究数据集](research-dataset.md)。

## 链路与责任

```text
院内系统（页面）→ 采集包 collection（仓库外）
                       ↓  scripts/structure_record.py
                 结构化病历 structured record + Markdown 审阅稿（仓库外）
                       ↓  records/research_dataset.py
                 研究数据集：固定列长表 + 归一化编码 + 研究阅读版（仓库外）
                       ↓
                 医生复核：接受 / 指出缺口 / 要求回原文
```

三段各有唯一 owner：**读取**由部署档案里的合格界面操作完成（只读优先）；
**清洗**由 `records/clinical_record.py` 完成，规则通用、不依赖具体医院；
**归一化与建表**由 `records/research_dataset.py` 完成，同样不依赖具体医院；
**判断与验收**由医生完成，代码不产生任何临床结论。结构化病历与研究数据集都是
工作副本，医院系统仍是正式病历的权威来源。

## 结构化病历的三条硬约束

1. **不补造。** 采集包里没有的字段写进 `missing`，不用医学常识或上一份文书
   填充。缺口清单本身就是产物的一部分，医生的时间应该花在真正的缺口上。
2. **不静默覆盖。** 两处记录不一致时，两个值都留在 `conflicts` 里，并标出
   是否同日、处置方式为 `kept_both_review_required`。冲突列表必须能让人一眼
   看出该回哪份原文核对；如果它经常误报，医生就会开始忽略它。
3. **每节可回溯。** 每个小节都带 `provenance`：来自哪份文书、文书创建时间、
   作者、以及选择该文书的依据（`document_precedence`／`only_read_document`／
   `unverified`）。依据是选择规则，不是逐字段证据；采集包若提供更细的
   来源，应在采集阶段就记清楚。

## 清洗规则

规则按「可验证、可测试」来写，全部有合成样例覆盖
（`tests/test_clinical_record.py`）：

| 规则 | 处理 | 反例 |
|---|---|---|
| 日期归一 | 统一为本地墙钟 `YYYY-MM-DDTHH:MM[:SS]`，**不做时区换算**；无法解析返回空并计入缺口 | 不把「9月23日」补成今天的年份 |
| 精度差异 | 两者在共同精度上一致时不报冲突 | `09:41` 与 `09:41:25` 是同一分钟，不算冲突 |
| 真实差异 | 共同精度上不同即报冲突，并标 `same_calendar_date` | `11:35` 与 `12:50` 必须保留双方 |
| 诊断拆分 | 仅当前缀编号成序列时按编号切分；标识符与量值不切 | `X12.345x010`、`直径5.5cm` 保持完整 |
| 诊断去重 | 按去标点后的键去重，保留首次表述与原始顺序 | 不因措辞接近就合并不同诊断 |
| 医嘱拆分 | 支持 `1.` `1、` `1）` 与段内编号 | 段首编号为 `2.` 时按本条处理，不丢弃 |
| 带药解析 | 拆出药名 / 单次量 / 途径 / 频次 / 总量；识别不到时保留原文并标 `uncertain` | 「按既往用药继续服用」不得被猜成具体剂量 |
| 文本规范 | 折叠空白、规范换行，不改写措辞 | 不做同义词替换 |

文书之间的阅读顺序是 **出院记录 → 疾病证明书**：前者含主诉、入院情况、入院
诊断、阳性辅助检查、住院经过、出院诊断、出院情况、出院医嘱与签字，是既往
病历结构化的主源；后者信息较少，用作补充与交叉核对。这只是**复核顺序**，
不是覆盖规则——第二名文书的内容不会消失，冲突会被列出来。

## 命令

```sh
PYTHONPATH=src python3 scripts/structure_record.py \
  --collection /absolute/path/outside/repo/history-<id>.json \
  --out-dir    /absolute/path/outside/repo/records \
  --record-id  history-<id> \
  --review-notes /absolute/path/outside/repo/review-notes.json
```

采集包与产物都必须在仓库之外；命令拒绝仓库内路径。输出为
`<record-id>.structured.json`（机器可读、供下游任务使用）与
`<record-id>.structured.md`（给人看的审阅稿）；加 `summary` 与 `csv` 格式后
还会输出研究阅读版 `<record-id>.summary.md` 与 `tables/<table>.csv` 研究长表。
产物权限 600。`--formats` 选择格式（默认 `json,md,summary,csv`），
`--tables-dir` 指定长表目录，`--review-notes` 传入仓库外的私有核实注记，
命中锚点的条目会在阅读版里就地标注 `※需核实 N`。命令只打印计数（就诊数、
缺口数、冲突数、未解析带药行数、各表行数、校验错误），**不回显患者内容**，
因此输出可以留在任务日志里。

校验不通过时命令以退出码 2 结束且不写文件；`validation_errors` 指出具体
违反的字段约束。

## 何时不得使用

- 采集包未标记任何已读文书：`provenance.basis` 为 `unverified`，该记录只能
  用于排查问题，不能作为病历底稿。
- 仍存在未处理冲突：列出冲突后必须回原文核对；不得由代码选择其一。
- 需要正式签署、归档或对外出具：结构化病历是工作副本，正式文书仍在院内
  系统内完成签署。
- 采集范围未获授权：未确认院方数据边界前，不得对真实患者运行本链路。

## 与工作流和验收的关系

本能力对应一期「既往门诊/住院病历收集与结构化」。结构化成功不等于该工作流
合格：还需要跨系统身份核对、查询范围与分页确认、缺失与矛盾标注，以及医生对
产物的验收记录。界面资格与逐项开放要求见
[院内系统调研与 KVM 界面资格](site-survey.md#kvm-界面资格与失败恢复)和[实施顺序与验收](roadmap.md)。

## 研究数据集

结构化病历忠实保留原文；跨病例统一管理还需要固定字段。第二层把诊断、用药、
检查、手术、质量问题抽成固定列的研究长表，补上与原文并列的归一化编码，并用
派生的研究编号替代直接标识。规则、表结构与合并约定见
[研究数据集](research-dataset.md)。两层都不做临床判断：判断与验收仍是医生的工作。
