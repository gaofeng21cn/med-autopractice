# 实施顺序与验收

本路线图是 MAP 的实施顺序与交付验收 SSOT。模块和状态 owner 见[架构文档](architecture.md)；九项一期工作的输入、产物和复核要求见[工作流](workflows.md)；机器可读的开放状态只看[能力目录](../contracts/capabilities.json)。

## 当前完成度判断

MAP 已有可复用的架构骨架、公共知识来源薄入口与合成任务闭环，但**功能完成度尚未达到一期预期**：一期九项能力全部保持 `planned`、`callable=false`，没有任何已验收的真实临床工作流。

已落地的部分包括：

- 医学提案、业务工作流、系统适配和共享任务状态的代码边界。
- 采集包清洗与结构化病历：通用的清洗规则、`map-structured-clinical-record.v1` 合同、校验器与审阅稿渲染，见[病历收集与结构化](clinical-record.md)。规则以合成样例验证，处理「不补造、不覆盖、可回溯」三条约束。
- 九项一期任务的语义依赖与阻断计划；部署依赖由仓库外 profile 提供，默认模板不包含院内身份资料。
- 首批住院病程草稿和医嘱调整的合成任务状态验证，包括患者/就诊绑定、事实版本复核、医嘱提交前确切提案确认、保存回读、截图引用、医生验收及不确定提交回查。
- 基于 `glkvm-native` 共享客户端的 KVM 适配接口和通用界面导航保护；没有真实医院 `HospitalUI` 实现。
- Framework 知识来源薄客户端、固定消费域与工作区/项目范围、提案知识引用传递和修订保留；临床来源选择和生产医学实现仍待完成。

仍未完成的关键部分包括：MAP 主 Skill 尚未驱动一个可部署任务运行时；SQLite 只用于合成患者；医学知识和本院制度规则没有生产实现；真实 UI 页面操作、中文病历输入和写后回读尚未取得资格；其余七项工作流目前以目录和依赖计划为主。仓库内的通用依赖模板（`contracts/site-dependencies.json`）全部 31 项为 `unmapped`，因为它是空模板；某次真实部署的资格进度记录在该部署的仓库外档案里，不进入本仓库。观察到系统或连通设备不等于业务能力通过验收。

结构化的产物是工作副本，不是正式病历：它不写回院内系统，也不改变业务能力的 `callable` 状态。

仓库自动化验证覆盖合成任务内核、清洗规则、知识客户端和保护逻辑；以当前测试运行结果为准。该结果不证明院内适配、医学正确性或临床可用性。

## 实施原则与统一验收

MAP 保持单一 Agent 项目、Codex 主 Skill 入口和模块化实现。业务工作流定义任务顺序、来源范围及审批门槛；医学组件按能力形成有来源的候选判断；医院适配器执行页面语义操作并回读目标对象。三者共用患者/就诊、来源事实、规则版本、提案、审阅和证据引用，不互相取得对方的决策权限。

独立安装同样遵循[Agent 共用基座](architecture.md#agent-共用基座)。生产医学组件沿 `ClinicalKnowledge` 和 `build_runtime` 的已有边界接入获准公共来源，验证 scope、精确版本、失效及引用修订；未来外部服务需求先绑定 Connect/provider 现有入口与凭证引用。设备和患者数据继续由原 owner 管理。UI 只在复核需要时选择，Agent 与 UI 必须回读同一临床任务及提案版本。

当前首版唯一设备执行方式仍是 `glkvm-native` 经 IP KVM 操作 Windows。源码不写院名、厂家、版本、页面路径、账号和患者内容；不假设院方提供 API/CLI，也不在 Windows 安装辅助程序。后续如果具体部署获准提供原生接口，可用适配器替换设备通道，但顶层任务完成语义不变。

每个能力独立开放。其合成测试必须覆盖缺失/冲突资料、错患者或错就诊、分页范围、事实版本变化、焦点或页面改变、中断恢复及不确定结果；真实部署还须按该能力取得授权的数据处理边界、界面操作档案、患者与就诊绑定、操作 trace、唯一目标对象回读、一手系统截图和医生验收证据。医嘱须在写入前由医生确认确切变更，写入后由医生验收；病历保存不等于正式签署。任何一项证据不足，该能力就保持不可调用。

## 阶段 0：可调用的 Agent 任务运行时

**目的：** 让主 Skill 能调用 MAP 的代码内核并取得可恢复的任务状态，而不是只说明该怎么做。

交付：

- 定义稳定的本地调用边界，接收能力、意图、患者/就诊受控引用和授权引用；返回任务状态、提案/产物引用、缺项、下一动作及证据引用。
- 让 MAP 主 Skill 通过该边界启动、查询、复核、修订和恢复任务；复用既有知识与设备入口，按实际需要接公共能力，不增加独立业务 UI 或额外 Agent 协调链。
- 把医学提案路由、业务工作流定义与任务内核组合起来，避免调用方手工拼装每个能力的 policy。
- 明确真实运行任务状态及证据的获准私有持久化 owner；保留合成 SQLite 与生产数据存储的硬隔离。先处理任务/审计事件的一致写入和崩溃恢复，再接临床数据。
- 落地院内系统调研工具链：`contracts/site-survey.schema.json` 定义仓库外 UI 调研档案，`scripts/site_survey.py` 只读输出语义操作状态和阻断项；专业 Skill 按 KVM 观察、只读探查、回读和资格撤销 SOP 执行。具体方案见[院内系统调研与操作档案](site-survey.md)。
- 高度特定的现场步骤用仓库外私有 playbook 固化：`contracts/site-playbook.schema.json` 定义格式，`scripts/site_playbook.py` 只读校验与展开，凭据只记录来源不记录值，含写入的 playbook 标记 `contains_write` 并需单独授权。

验收：一个合成任务能由宿主入口创建、跨进程恢复、查询、审批或修订；重复 `request_id` 返回原任务；故障注入不产生丢失的审计步骤或重复系统提交；入口不能通过默认设置访问真实院内配置。

调研工具验收：外部 survey pack 能被加载，`observed`/`qualified`/`revoked` 状态和证据引用按合同校验；包含患者正文、截图字节或秘密字段时拒绝；仓库内路径拒绝；输出不连接设备、不执行输入。

playbook 工具验收：外部 playbook 目录能被加载并展开为有序步骤；步骤 ID、KVM 原语、副作用等级和失败策略按合同校验；引用未在 survey pack 中的系统时拒绝；含 password/token/patient 等字段或位于源码仓库内时拒绝；只读列出不连接设备。

当前状态：`runtime.py`、`scripts/map_runtime.py`、合成 `HospitalUI`、公共知识来源薄入口与对应测试已落地。真实私有持久化 owner、崩溃恢复的跨进程审计一致性和正式适配器仍未完成，阶段 0 尚未整体关闭。

## 阶段 1：当前住院患者双主线

**目的：** 按既定首批范围先完成当前住院病程草稿和医嘱调整，不因历史数据整理而延后当下临床工作。

交付：

- 通过 UI 适配读取指定就诊的必要既往记录、当前医嘱、相关检验/检查和护理事实，并形成有来源的任务快照。
- 先打通病程草稿路径：医学组件生成病程候选，制度规则组件校验必需部分、适用时效和缺项；不得从空白推断阴性，不得编造未发生的诊疗活动。建立草稿保存、重新打开后的逐段内容回读和最终医生验收；纯 KVM 中文输入未通过资格测试前仅交付草稿，不自动回填。
- 再打通医嘱调整路径：读取当前医嘱、新检验检查结果、护理记录和适用本地目录；产出逐项候选及依据。医生对确切患者、就诊、资料版本和整批拟变更作提交前批准；适配器逐项录入并回读。
- 两条路径共用任务状态、事实快照、系统操作 trace、失败恢复与一手截图，不共用医学判断逻辑；病历和医嘱分别选择医学知识组件。

验收：合成页面通过错患者/就诊、资料缺漏、他人同期修改、输入焦点变化、中文输入不完整、部分医嘱失败、超时响应丢失和人工接管恢复。部署端分别验证病程全文与医嘱关键字段、目标对象、状态、操作 trace、系统原图和医生验收。正式病历签署仍由医生完成；医嘱“已录入”不等于“已执行”。

## 阶段 2：既往资料收集与结构化

**目的：** 完成一期既往门诊与住院资料整理，同时让其复用阶段 1 已建立的事实、来源和审阅底座。

交付：

- 为只读能力提供独立产物和医生审阅状态，不强制调用医嘱写入路径；医学提案仅在确需临床解释时按能力配置。
- 结构化就诊时间线、诊断、手术、病理、用药、检验检查及文档索引；保留跨来源冲突、单位、发生/记录时间、对象状态、查询范围、分页覆盖及缺失原因。
- 支持明确的患者集合、就诊/日期范围、覆盖清单、失败明细、暂停和恢复；不默认“全部患者”。
- 病历时效提醒、出院病历整理与审核依赖经确认的部署制度和文书状态，和医学判断分开实现。

验收：合成资料集覆盖重复记录、同名患者、同一事实多来源冲突、未查询/未发现/明确否认/不可识别的区别、分页遗漏和中断续跑；输出可逐项追溯源对象与采集范围。资料不完整时不得宣称完整，且历史诊断/用药不得自动成为当前状态。

## 阶段 3：扩展其他当下工作

按共享依赖逐项交付，而非一次开放整个目录：

1. 新收住院医嘱：结合已核实入院资料、过敏、当前治疗、医嘱目录及医生明确诊疗计划，形成逐项确认后录入和回读。
2. 出院带药：结合当前用药、过敏、医生出院计划及目录，提示差异和待确认项；确认后录入并核对剂量、规格、途径、频次、疗程与数量。
3. 门诊结构化病历和医嘱：绑定本次门诊就诊，区分患者陈述、既往资料、实测体征与医生判断；缺失项明确提示。
4. 医嘱组套：导入已批准的本院方案和本地字典，产生有版本和生效日期的差异候选；临床负责人审阅后才可发布。
5. 出院病历整理与审核：对照本院有效制度及文书状态列出缺项、矛盾和时效提醒；不得倒签或覆盖已签记录。

每项使用独立合成样例、schema 和验收记录；不根据公开标准臆造本院用药字典、组套内容或文书时限。

## 阶段 4：既往资料批处理

在阶段 1 单患者流程稳定后，扩展门诊与住院历史资料范围处理。通过医院授权的明确对象/日期范围分批读取，保留分页游标、去重依据、源对象标识、失败记录和恢复点。历史数据结构化产物先交医生审阅；未经另行设计，不自动覆盖当前诊断、医嘱或已签病历。

验收：合成大批次验证暂停续跑不漏不重、重复源去重、跨系统身份映射、逐条来源、部分失败和撤销/删除政策。部署存储、备份、访问控制与保留期限须在真实数据接入前获院方认可。

## 逐部署资格与运行观察

对当前连接的院内系统逐项建立私有操作档案：系统和版本、账号角色、患者/就诊标识、导航和搜索范围、分页、读取字段、写入效果、错误恢复、回读位置和证据保留规则。界面步骤从实际观察提取，不把某一院的坐标或产品分支固化到 MAP 通用仓库。

资格工作贯穿阶段 1 至阶段 4：先在获准环境完成只读读取与回读，再按医院批准范围监督草稿保存和医嘱录入。每项资格绑定适用系统版本、角色、分辨率和操作证据；界面、设备、权限或输入法变化撤销受影响资格并重验。一次院内资格只开放对应部署和对应能力。

运行中比较同类任务的完成时间、医生修改量、人工接管次数、成功率、关键字段错误率和模型 token（区分缓存）；身份、来源和医嘱关键字段核对不得为降低 token 而省略。

## 暂缓范围

专病队列和动态随访留待一期之后。当前不建设独立 UI，不做未经批准的医院 API/CLI，不预设临床模型或知识库供应商，也不将 `glkvm-native` 的通用远控连通性当作 HIS/PACS 资格。
