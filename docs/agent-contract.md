# Agent 调用契约

Codex 主 Skill 将用户意图交给 MAP 任务内核，医生在同一会话中审核草稿与差异。独立安装与分步使用见[快速上手](getting-started.md)。

## 入口与实现分工

主入口为 `skills/med-autopractice/SKILL.md`，由仓库根部的 Codex 插件清单分发。Skill 负责理解医生目标、选择能力与组织复核；`medicine` 产生医学候选内容，`workflows` 定义业务资料范围与审批门槛，`TaskEngine` 编排状态，`adapters` 实施系统语义操作。模块与状态 owner 以[架构文档](architecture.md#模块与合同归属)为准。CLI/MCP 只在需要确定性调用或设备操作时提供工具通道。MAP 可独立调用，通用知识、连接与按需 UI 遵循[Agent 共用基座](architecture.md#agent-共用基座)；初期不建立额外 Web UI、常驻临床服务或多 Agent 控制链。

任务过程依次包括意图解释、患者和就诊绑定、事实和规则读取、草稿或差异、必要的医生批准、获准提交、目标系统独立回读及医生最终验收。需要修订时沿用同一任务并重新核对版本。

本地入口为 `TaskRuntime` 与 `scripts/map_runtime.py`。合成任务显式指定 `--store`，站点任务显式指定 `--site`。两种调用返回同一任务 ID、当前状态、提案、缺项和回读结果。站点调用另支持 `batch` 汇总只读清单，`refresh` 重新准备同一个尚未提交的任务。站点写入依赖医生批准的提案摘要和事实版本，写入后独立回读供验收。只读任务返回带依据的结果供医生验收。详细用法见[本地部署](local-deployment.md)。

## 请求至少表达

- `request_id`：调用方幂等请求标识；重复请求应查询原任务，不重复写入。
- `capability_id`：来自能力目录的具体目标；自然语言可在入口解析成该目标。
- `intent`：医生要完成的事情及非目标。
- `subject_ref`：绑定医院、患者、就诊的受控引用；不是单凭姓名或床号。
- `input_refs`、`facts_revision`、`as_of`：事实来源、已核对版本和资料时间截点。
- `authority_ref`：院内访问范围、允许的动作、审阅/正式写入条件；不将用户意图文本视为任意授权凭据。
- `review_ref`：需要时绑定医生、患者/就诊、确切拟变更和事实版本的批准记录。

患者正文只进入批准的数据处理面；凭据与设备 token 不进入调用参数。既往批量收集需要额外的队列/日期范围和覆盖要求，不用“全部患者”作隐含默认值。

## 响应至少表达

`task_id`、`capability_id`、`status`、`artifact_refs`、`evidence_refs`、`missing_information`、`next_action`、`execution_receipt`。提案还须绑定 `schema_version`、`generator_ref`、`knowledge_refs`、`cited_fact_ids` 和完整正文的摘要；换医学模型或知识版本后原批准不能沿用。`runtime.revise` 在未明确传入新知识引用时保留原提案引用；明确传入时将新引用纳入摘要并要求重新审批。来源的授权、接受版本和有效性由 Framework 公共知识接口负责，MAP 不在任务库内复制正文。状态需区分：资料范围不完整（`needs_information`）、仅可审阅草稿而写入未验收（`draft_only`）、草稿待提交、需要提交前复核、事实版本已变化、执行结果不确定、系统已回读待医生验收、要求修订、医生已接受。成功产生草稿只代表草稿完成，系统回读只代表目标对象已核验，均不等于医生验收或正式签署。

写入后必须从目标系统独立回读对象、患者、就诊、状态与确切内容。界面操作绑定一手截图，原生接口或中间件绑定重新读取的版本化资源或受控证据快照，以及观察时间。医生在宿主中接受结果或提出问题。超时后查询原系统，批准版本或临床事实有变化时重新核对。证据正文放在院方认可的存储。

内部幂等键只用于 MAP 任务追踪，不假设院内 GUI 能按该键查询。提交响应丢失后，MAP 保持 `execution_uncertain`；KVM 适配器以完整任务中的患者、就诊、目标列表、时间和确切内容查找可见对象。只有唯一对象匹配时才回读，缺失或多个候选均不自动重放写入。合成库与临床站点库分别绑定身份。站点库在同一数据库事务保存任务与审计事件，以版本比较保护并发更新。实际部署使用院方指定的数据存储和访问策略。

任务固定创建时的执行策略；重启后的当前策略若不同，提交或修订转为 `needs_policy_review`，不得把旧批准条件用于新规则下的写入。站点策略绑定部署描述、依赖档案和适配器源码版本，规则记录院方批准引用。取消或更新授权时适配器从权限服务回读当前状态。

## 可用性与未来资格

公开运行时随包提供合成任务与显式站点装配。临床能力逐项列在能力目录中。站点开放真实患者任务前须落实获准的存储与权限，完成患者绑定、实际适配、操作回读和医生验收。

共用基座不以跨宿主托管为前提：MAP 已通过薄客户端使用 Framework 知识来源，设备操作复用 glkvm-native；后续外部连接按现有 owner 合同接入。MAP 继续持有临床任务状态、证据和权限边界。若需 Framework Package 托管或标准智能体封装，按届时真实合同单独验证安装、可调用性与副作用路径；不能把只读 handler 当作 GLKVM 或院内写入执行器。必要 UI 必须读取和操作同一 `TaskRuntime` 对象，医生复核绑定同一提案摘要，页面重开不重新创建任务或重放临床写入。
