# 临床工作流与规则维护

全部一期功能见 [产品范围](product.md)；机器可读状态见 [能力目录](../contracts/capabilities.json)。

本页只定义业务任务的输入、产物和复核要求。医学判断与业务工作流的代码边界以[架构文档](architecture.md#模块与合同归属)为准；一期九项和后续两项在 `workflows/catalog.py` 定义语义依赖，并在[合成站点](local-deployment.md)通过本地入口演练。真实院内字段和规则由各站点逐项验收。

`python3 scripts/site_plan.py revise_orders` 可输出医嘱调整所需的读取、规则、医学提案、医生提交前确认、系统录入、回读和最终验收步骤及阻断项。命令默认读取未配置的通用依赖模板；部署方可通过 `MAP_SITE_PROFILE` 指向仓库外的私有 JSON profile。命令只读本地元数据，不连接设备或患者。`observed` 不等于操作合格；`dependencies_qualified` 也不是能力目录的 `callable` 或临床执行许可。初版列出保守的资料源全集；实际任务仍需按医生目标、时间范围与相关性选择结果来源，不能机械读取所有历史检查。

## 用户提出的任务如何落位

| 工作流 | 主要输入和产物 | 必须保留的核对与复核 |
|---|---|---|
| 既往门诊/住院病历收集与结构化 | 就诊时间线、诊断、手术、病理、用药、检验检查及文档索引 | 跨系统身份、分页/查询范围、时间和单位；标出缺失与矛盾，不声称全部资料完整 |
| 医嘱组套建立与动态更新 | 科室已批准方案、本院药品/检查字典、现有组套 → 版本化组套提案 | 适用条件、排除条件、必填变量、剂量/途径/频次及字典映射由临床负责人审核；更新先形成差异，不自动替换生效版 |
| 新收患者医嘱 | 医生明确诊疗计划、当前病情、过敏/用药等必要信息 → 待审医嘱草案 | 明确区分机械录入与诊疗决定；缺失信息阻止相应项目推进，医生逐项或按可审阅批次确认 |
| 根据结果和护理记录更新医嘱 | 新结果、护理记录、当前医嘱和医生判断 → 变化摘要及调整提案 | 异常结果触发提醒和人工临床判断，不按阈值自行启动、停用或调整治疗；执行前检查其他人是否已改医嘱 |
| 出院带药 | 当前用药、用药核对、医生出院计划 → 带药草稿与差异 | 药物延续/停用、剂量、疗程、数量、重复或潜在问题由医生核定；患者教育内容与已确认方案一致 |
| 住院日常记录 | 实际临床事件、可靠来源和医生补充 → 相应记录草稿 | 制度规定决定需要哪些记录和时限；没有开展的活动不能生成“已完成”记录，正式签署由医生完成 |
| 门诊结构化病历 | 本次主诉、病史、实际查体、检查及医生评估 → 结构化草稿 | 关键缺失明确提示，不补造阴性体征；确认对应本次门诊就诊 |
| 出院后整理、审核和时效提醒 | 全住院文档、签署状态、归档要求 → 缺项/冲突/时限清单及修订草稿 | 院内正式规则与文档状态为依据；保留实际创建与修改时间，不倒签或覆盖已签记录 |
| 专病队列、整理与随访 | 经批准的纳入定义、字段字典、临床事实 → 队列条目与随访待办 | 临床照护和科研用途区分；研究用途另核相应授权。纳入/排除和结局可追溯，失访/未测不等于阴性；联系患者须在授权渠道和范围内 |

「既往门诊/住院病历收集与结构化」已有可运行的产物环节：采集包经 `scripts/structure_record.py` 清洗为结构化病历，规则与边界见[病历收集与结构化](clinical-record.md)。清洗只整理已采集内容并标出缺口与冲突，不补齐字段，也不改变该工作流的验收要求。

PACS 第一阶段定位为检查定位、正式影像报告读取和供医生调阅原图。不得把 KVM 压缩画面自动当作可诊断影像，也不将“理解 PACS 操作”扩展为自动影像诊断。

## 知识与规则怎样维护

“十八项核心制度”不能做成 18 段泛化提示词。以当前有效的院内制度、病历书写规范和科室流程建立规则记录：适用对象、触发事件、需要的事实、产物要求、截止规则、例外、来源、有效期及审核人。此次未获取并核验具体院内文件，暂不写死各记录的法定/院内时限。

临床知识、医院制度、操作界面和患者事实是四种不同资料：临床知识支持医生判断；制度规定流程与产物；界面说明怎样操作；患者事实描述实际发生什么。更新其中一种不应静默改变其余三种。

组套或规范更新先形成候选版本和差异，经临床负责人认可后启用；保留旧版本与适用时间。成功点击一次界面不等于临床知识正确，医生改过一次草稿也不自动形成全科默认规则。
